1. Project Overview

MedBill AI is a full-stack system that automates the scrutiny of medical bills submitted by PSU (Public Sector Undertaking) employees under the CPRMSE / CPRMSNE medical reimbursement schemes of Coal India Limited (CIL) and its subsidiaries.

🎯 What Problem Does It Solve?

Medical claim officers at CIL/SECL manually review hundreds of scanned hospital bills. Each bill must be checked against CGHS rates, room entitlement, hospital empanelment, documentation completeness, and fraud indicators. This is time-consuming and error-prone. MedBill AI automates the extraction and initial validation, flagging issues automatically.

Key Capabilities

  • OCR Extraction — Converts scanned bill PDFs to machine-readable text via Tesseract
  • AI Structuring — Uses a local LLM (Phi-3 via Ollama) to parse OCR text into structured JSON
  • Rule Validation — 39 deterministic rules check eligibility, rates, documentation, fraud
  • CGHS Rate Lookup — Matches each line item against the official CGHS rate database
  • Hospital Empanelment Check — Verifies treating hospital is on the CIL empanelled list
  • Interactive Dashboard — Review, edit, and save extracted data via a web UI
  • 100% Local — No cloud API calls; all AI runs on the local machine via Ollama

Technology Stack

🌐 Frontend

  • Vanilla HTML + CSS + JavaScript
  • Server-Sent Events (SSE) for live progress
  • Drag-and-drop PDF upload

⚙️ Backend

  • Python 3.11
  • FastAPI + Uvicorn
  • Async task processing

🗄️ Database

  • SQLite with FTS5 full-text search
  • CGHS rates table (3,000+ procedures)
  • Hospitals table (1,000+ entries)

🤖 AI / OCR

  • Tesseract OCR (via pytesseract)
  • pdf2image — PDF → images
  • Ollama (Phi-3:3.8b) — local LLM

3. Processing Pipeline

When a PDF is uploaded, it goes through a 4-stage pipeline. Each stage reports progress to the dashboard via SSE.

📄 PDF Upload
→
🔧 PDF Repair
→
📷 OCR
→
🤖 AI Parse
→
✅ Validate
→
💾 Save & Display

Stage 1 — PDF Repair

Uses ghostscript (gs) to re-distill the uploaded PDF, fixing any structural corruption. The repaired file is saved as data/processed/bills/{id}_repaired.pdf. If GS is not installed, the original PDF is used as-is.

Stage 2 — OCR Extraction

The repaired PDF is converted to page images using pdf2image (backed by poppler's pdftoppm). Each page image is pre-processed (grayscale, adaptive threshold, deskew) then fed to Tesseract for text extraction. Per-page confidence scores are averaged to produce an overall OCR confidence metric (0–100%).

PDF → page_1.png, page_2.png, ... → OCR text per page → concatenated text

Stage 3 — AI Structuring (Phi-3)

The raw OCR text is sent to a locally-running Phi-3:3.8b model via the Ollama API. A carefully crafted prompt instructs the model to extract specific JSON fields. If Ollama is offline, the system falls back to regex-based rule extraction.

Extracted fields include: patient name, employee ID, UHID, relationship, hospital name/city, NABH status, admission/discharge dates, diagnosis, treating doctor, bill number/date, total/net/advance/balance amounts, and individual line items.

Stage 4 — Rule Validation

The extracted BillData object is passed to the ValidationEngine. Each of the 39 rules is evaluated and returns a ValidationResult with status (PASS/FAIL/WARN), a human-readable message, and optional financial impact.

server.py — The Backend

This is the heart of the application. It serves the dashboard as static files and exposes the REST API. Key responsibilities:

  • Startup: loads all previously processed bill JSON files into memory (processed_bills list)
  • Upload endpoint: accepts PDF, saves to data/uploads/, creates a job record, starts an async background task
  • Async processing: runs the 4-stage pipeline in a thread pool executor (via loop.run_in_executor) to avoid blocking the event loop
  • SSE stream: the /api/jobs/{id}/stream endpoint polls the job dict and sends updates as text/event-stream
  • In-memory storage: jobs and bills are stored in Python dicts. On restart, bills are reloaded from JSON files. Jobs are not persisted.

scripts/extract_bill.py — OCR + LLM Extraction

Contains the BillExtractionPipeline class and supporting data classes (PatientInfo, HospitalInfo, AdmissionInfo, BillData).

  • process_bill(pdf_path) — main method: repair PDF → OCR → LLM/regex → return BillData
  • _ocr_page(image) — preprocesses image, runs Tesseract, computes confidence
  • _select_key_pages(ocr_text) — picks the most informative pages to send to the LLM (avoids token limits)
  • _call_ollama(prompt) — sends prompt to Ollama HTTP API, retries on failure
  • _extract_with_regex(text) — fallback extraction using 30+ regex patterns
  • _extract_field(text, patterns) — utility: tries each pattern, returns first match group

scripts/validation_engine.py — Rule Engine

The ValidationEngine class loads rules from data/validation_rules.yaml and evaluates them against a claim dict. Returns a list of ValidationResult namedtuples.

  • validate_claim(claim) — top-level method, calls all private check methods
  • _parse_date(raw) — multi-format date parser (ISO, DD/MM/YYYY, DD-MM-YYYY, etc.)
  • find_cghs_rate(name) — FTS5 + LIKE fallback lookup in cghs_rates table
  • verify_hospital(name) — FTS5 + LIKE lookup in hospitals table
  • SQLite connection uses row_factory = sqlite3.Row for dict-style column access

data/validation_rules.yaml — Rules Definition

Structured YAML with 15 sections (39 rules). Each rule has: rule_id, name, description, severity (ERROR/WARNING/INFO), source (SOP/OM reference), and checks. The engine reads thresholds and entitlement tables directly from this file so rules can be updated without code changes.

7. Dashboard Guide

📊 Dashboard Tab

  • Stats row: Bills Processed, Rules Passed, Issues, Total Claimed
  • Bill selector (when >1 bill processed)
  • 4 info cards: Patient, Hospital, Admission, Financial
  • Field Confidence panel — colour-coded bars (red = below 80%)
  • Review & Edit panel — correct any OCR errors
  • Line Items table — all extracted charges
  • Validation Results grid — pass/fail/warn for each rule
  • Extraction Metadata — method, OCR %, pages, timestamp

📤 Upload Tab

  • Drag-and-drop or click-to-browse PDF upload
  • Processing options: LLM on/off, OCR DPI, max pages
  • Live pipeline progress (4 steps with progress bars)
  • SSE stream: auto-redirects to Dashboard on completion

9. Setup & Running Locally

Prerequisites

Install these system tools before pip installing requirements:

# macOS
brew install tesseract poppler ghostscript

# Ubuntu / Debian
sudo apt-get install tesseract-ocr poppler-utils ghostscript

Step-by-Step Setup

# 1. Clone repository
git clone https://github.com/kumarnitn/MEDICAL-BILL-SCRUTINY-SYSTEM.git
cd MEDICAL-BILL-SCRUTINY-SYSTEM

# 2. Create and activate virtual environment
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate

# 3. Install Python dependencies
pip install -r requirements.txt

# 4. Set up database (creates SQLite schema)
python scripts/setup_database.py

# 5. Parse CGHS rate card (requires raw text file from PDF)
python scripts/parse_cghs_rates.py

# 6. Parse hospital empanelment list
python scripts/parse_hospital_list.py

# 7. (Optional) Install Ollama for AI extraction
#    https://ollama.ai — then:
ollama pull phi3:3.8b

# 8. Start the server
python server.py
#    or via uvicorn:
uvicorn server:app --host 0.0.0.0 --port 8000 --reload

Open your browser at http://localhost:8000

Tip: If Ollama is not running, the system falls back to regex-based extraction automatically. You can still upload bills — they'll be processed with lower accuracy but without requiring GPU or RAM for the LLM.

10. Deployment

🐳 Docker (Recommended)

docker build -t medbill-ai .
docker run -p 8000:8000 -v $(pwd)/data:/app/data medbill-ai

The Dockerfile installs tesseract, poppler, and ghostscript automatically. Mount data/ as a volume to persist the database and uploaded bills between restarts.

☁️ Render / Koyeb (Cloud)

The render.yaml and start.sh are configured for one-click deployment on Render.com or Koyeb. The service type is docker. PORT is set to 8000 via environment variable. Note: Ollama (local AI) will not be available in cloud deployments — the system will run in regex-fallback mode.
